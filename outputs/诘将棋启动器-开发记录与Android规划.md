# 诘将棋启动器：开发记录与 Android 移植规划

更新时间：2026-09-05

这份记录用于继续开发时快速恢复上下文。文中把“已验证”“已写入但尚未验收”“后续计划”分开，避免把临时方案误认为最终功能。

## 一、最初目标和范围变化

最初的设想是：基于 Shogi Explorer，加上 shtsume、YaneuraOu、中文启动器、剪贴板 KIF 导入、普通棋局复盘和诘将棋训练记录。

经过实际检查后，需求收敛为诘将棋专用启动器：

- 核心是 5/7/9 手诘将棋题库和解题训练；
- 需要独立的本地题库，不把诘将棋 KIF 作为核心格式；
- 需要标记题、错题、重刷、完成数、标记题完成数和成就；
- 剪贴板导入、KIF、全局复盘、普通棋局分析暂时砍掉；
- 基础功能完成后，再集中做视觉和交互美化；
- Android 版本可以复用题库和规则核心，但 UI 需要按触屏重新设计。

### 开发过程时间线

1. 检查原有 Shogi Explorer/Java 包的菜单、字体、JAR 和引擎入口，确认中文乱码和缺少诘将棋交互是两个独立问题；
2. 尝试在旧界面上接入题面、记录器和引擎，发现它更适合普通 KIF/棋局查看，不适合作为诘将棋训练主界面；
3. 收敛为独立的本地 HTML 启动器，先完成 SFEN + 线性解答、走子/打入/升变、错着记录、标记和成就；
4. 用 Tanuki 公开精选数据建立 457 题基础集，做桌面和窄屏视觉调整，并验证记录不会因重复做题重复计成就；
5. 为解决题数不足，下载同一公开仓库的生成数据，按局面哈希去重，形成精选 457 + 扩展 627 = 1084 题，并同步导出 SFEN/meta.tsv；
6. 下载 shtsume v1.2.6 及 Windows 运行时依赖，验证其 CLI/USI 行为；由于长驻管道在本机不稳定，改用 server.ps1 按次调用并加入进程级超时和前端回退；
7. 加入引擎状态、玉方自动应手、可选严格手数失败重开、悔一步、重新开始、错题/标记重刷、今日挑战、计时/最快成绩、连续天数和成就；
8. 对 1084 题逐题做页面加载烟雾测试，再做完整解题、引擎关闭回退、升变、题库切换和严格手数测试，最后重新整理便携压缩包。
9. 曾尝试把引擎改为题面出现即后台预热当前局面，并把默认时限压到 1 秒；同时第二轮重做中文字体、棋盘、棋子和持駒的现代化视觉层。该预热主变方案后来按第 11 步反馈撤销。
10. 用 .NET 8 WinForms + WebView2 包装训练页面，生成可双击的 Windows x64 自包含程序；保留 Start.bat 作为唯一启动入口。
11. 根据使用反馈撤销“用户着法必须等于引擎首着”的判题思路：合法王手直接接受，YaneuraOu 只负责快速生成玉方应手；取消用户可调引擎时限，训练结束只由题目手数决定。

## 二、方案选择过程

### 1. 为什么没有继续把 Shogi Explorer 当成主程序

Shogi Explorer 适合查看 KIF 和棋局复盘，但它的棋局读取入口主要是 KIF 解析，原有棋盘也没有现成的诘将棋“用户落子—玉方应手—判定正误”交互流程。

它可以显示一个 SFEN 局面，但不能直接把 SFEN 题目变成完整的诘将棋练习。因此，继续在它上面堆菜单只能得到“能显示题面、不能真正做题”的半成品。

当前结论：

- Shogi Explorer 只适合作为历史兼容或复盘工具；
- 诘将棋主程序应当是独立的训练界面；
- 后续基础版以本地 HTML/桌面启动器实现，避免重复开发普通棋局复盘。

### 2. 为什么没有直接把 500 万题全部打包

YaneuraOu 公开了按 3/5/7/9/11 手分类的超大 SFEN 题库，适合作为扩展源，但体量大，而且“数量多”不等于“训练体验好”。本项目先把可随包使用的数量扩到 1084 题，同时把默认精选集和扩展练习集分开显示，不把扩展集冒充精选集。

### 3. 当前精选题库来源

当前采用 `tokuhirom/tanuki-tsume-shogi` 的公开题库数据。该项目是 MIT 许可，并在开发说明中记录了唯一解、无駒余り、规则验证和多样性过滤等设计，适合做第一版内置精选题库。

当前转换出的题量：

- 精选集：5 手 296 题、7 手 132 题、9 手 29 题，合计 457 题；
- 扩展练习集：5 手 0 题、7 手 86 题、9 手 541 题，合计 627 题；
- 全部：1084 题。启动器默认进入精选集，扩展集用于增加练习量。

题库中保留了初始局面、手数、解答手顺、质量标记、评分、哈希、集合类型和来源。解答手顺只用于题目手数、参考手顺和引擎不可用时的应手回退，正常训练不据此否定用户的合法王手。

题源和授权文件位于安装包的 `puzzles` 目录：

- `puzzles/mate5.sfen`、`puzzles/mate7.sfen`、`puzzles/mate9.sfen`：便于其他工具读取的 SFEN；
- `puzzles/mate5.meta.tsv`、`puzzles/mate7.meta.tsv`、`puzzles/mate9.meta.tsv`：题目编号、评分、质量标记、哈希、集合类型和来源；
- `puzzles/TANUKI-LICENSE.txt`：MIT 授权文本；
- `puzzles/README.txt`：题源、扩展方式和许可说明；
- `puzzle-data.js`：本地解题页面直接使用的带解答数据。

日本将棋连盟每日诘将棋、詰将棋パラダイス等来源暂时只作为“网上精选”入口，不直接复制和重新分发受版权约束的题面。这样既能给用户更多高质量来源，也不会把网页内容的授权问题混进安装包。

扩展集的来源是 Tanuki 仓库中的生成数据，去重后加入 7/9 手训练；页面明确标记“扩展题”，精选集仍然是默认入口。今后若引入 YaneuraOu 的超大公开题源，应先做验证、去重、难度和人类可解性筛选，再作为新的练习包，而不是一次性塞入全部文件。

## 四、主要技术难点和处理方式

### 难点 1：SFEN 不是 KIF

SFEN 只描述一个局面和持駒，不包含完整解答。KIF 解析器通常从标准开局或手合开始，不能直接把任意 SFEN 当成一盘可复盘棋局。

处理方式：

- 本地题库以“局面 + 解答手顺”作为独立数据模型；
- 不再强行把 SFEN 伪装成 KIF；
- 解题页面直接从题库模型构造棋盘。

### 难点 2：诘将棋不是普通将棋对局

需要处理：

- 攻方必须连续王手；
- 玉方必须按题目规则应手；
- 打入、吃子、升变会改变棋盘和持駒；
- 题目可能包含升变、持駒打入和防守方应手；
- 不能只比较最后一个局面。

当前训练采用“规则校验 + 引擎应手”的判定边界：用户着法只需是攻方合法着法并形成王手即可接受；YaneuraOu 根据用户刚刚形成的局面生成玉方应手，不比较用户着法和题库主线，也不负责证明整题是否为诘。题库线性手顺只保留手数、参考答案和引擎不可用时的回退用途。

这意味着“训练完成”是按题目预设手数完成一次训练，不等同于引擎证明了该分支是唯一解或必诘。未来若要展示多个分支、做完整詰み验证，再把题库格式扩展为解答树和独立验证报告。

### 难点 3：题库质量和版权不能混为一谈

随机生成或随机抽样可以快速得到很多局面，但不代表题目适合训练。另一方面，网上有作者署名的题集不能默认下载后重新打包。

当前策略：

- 内置 MIT 许可、带验证说明的公开精选数据；
- 其他高质量来源只做在线链接；
- 每个随包题库都保留来源和许可文件；
- 未来增加来源时，先确认数据许可，再决定“内置”还是“在线打开”。

### 难点 4：Windows 中文乱码和便携启动

曾经出现过窗口标题能显示、菜单却变成方框的问题，也出现过 JAR 更新时遗漏 Java record 内部类导致程序打不开的问题。

处理经验：

- Swing UI 字体不能只依赖系统默认字体，要显式选择能显示中文的字体；
- JAR 更新类文件时，内部类文件也必须一起更新，例如 `TsumeDatabase$Puzzle.class`；
- 启动脚本必须切换到自身目录，不能依赖用户当前命令行目录；
- 每次打包后都要进行“解压到全新目录—双击启动—关闭—再次启动”的验证。

### 难点 5：本机文件记录的边界

独立窗口使用随机本地端口，不能把浏览器 `localStorage` 作为训练记录的主存储，否则每次端口变化都会产生新的站点分区。本版由本地服务将训练记录、设置、统计和成就写入 `%LOCALAPPDATA%\TsumeLauncher\training-data.json`，EXE 与同目录的 `Start.bat` 共用同一份文件；题库和引擎资源不写入该文件。

写入时先生成临时 JSON，再替换正式文件，避免程序中断时留下半截记录。若本地文件不可读或不可写，界面会显示记录存储异常，而不会把数据悄悄写到另一个浏览器分区。

后续可增加：

- 导出/导入训练记录 JSON；
- 记录备份文件；
- Android 使用 Room 或 DataStore 保存；
- 记录格式版本号，方便桌面版和 Android 版迁移。当前版本不迁移旧浏览器 `localStorage` 记录，现有题目主键和记录字段保持不变。

### 难点 6：美化后的响应式 CSS 优先级

第一轮美化时把桌面两栏网格放在了原有媒体查询之后，导致 390px 屏幕仍然使用 `318px + 560px` 的桌面列宽，页面出现横向滚动。通过浏览器计算样式定位到 `.layout` 的网格列定义后，在后置的窄屏媒体查询中重新声明单列布局，并用桌面/手机回归测试确认棋盘和所有面板都能收缩。

### 难点 7：引擎自动应手和桌面进程边界

shtsume 适合做诘将棋求解和题源验证，但不适合承担“用户刚下任意合法王手后立即给玉方应手”的交互职责。本版因此把职责分开：YaneuraOu 作为常驻 USI 应手 worker，启动时完成握手和 NNUE 加载；用户落子后只发送当前局面的 position 和固定快速节点预算，收到 bestmove 后立即回传。

诘将棋题面有时省略攻方玉，而普通将棋引擎要求双方都有王。服务端只在发送给 YaneuraOu 的内部副本中补一个不影响实际棋盘的虚拟攻方王，并准备多个远离战斗区域的位置作为候选；返回给页面的仍是实际题面上的玉方着法。YaneuraOu 不比较用户着法、不验证题库首着，也不证明整题为诘。

如果常驻进程不可用、没有合法应手或接口异常，前端不把这当作攻方错误；优先尝试题库回退应手并记录回退次数。普通训练的规则边界只有攻方合法、必须王手和题目手数；严格手数开关只负责超出提交次数后重开。

### 难点 8：题库数量、质量和训练体验的平衡

Tanuki 的公开仓库同时有精选数据和更大的生成数据。扩容时按局面哈希去重，保留精选题编号，把新增局面编号放在各手数的扩展区；SFEN、meta.tsv 和页面数据一起导出，避免用户看到的数量与实际列表不一致。默认精选、扩展/全部切换、错题重刷和今日挑战分别解决质量、数量和持续训练的问题。

参考其他诘将棋平台后加入的体验点包括：提示只揭示一个关键位置、看答案暂停计时、标记题和错题回收、每日固定题、计时/最快成绩、连续天数、成就、跳过和键盘快捷键。多解题、解答树、同步账号和完整规则验证暂不假装已经实现，列入后续数据模型升级。

平台参考与取舍：
- Tanuki：关注规则校验、唯一解/无駒余り检查、预生成题库和本地记录；
- 詰将棋パラダイス：关注题目标签、收藏、提示、解答说明和错题回收思路；本包只保留合法公开来源，不复制网页题面；
- 詰将棋/逃げ将棋移动端：关注错题复习、下一格提示、解答摘要和引擎复核思路；
- Tsumemi：关注每题计时、正确/错误/跳过统计和可导出训练记录的后续方向；
- YaneuraOu：作为随包常驻的快速玉方应手引擎；超大公开题源仍不直接把 500 万级数据塞进桌面包。

当前刻意没有加入账号同步、联网排行榜、音效、复杂解答树和剪贴板/KIF，因为这些功能会扩大范围，且与“诘将棋专用启动器”目标不一致。

## 六、Android 版本规划

### 总体建议

Android 版不要把桌面版的三栏布局直接缩小。建议复用同一套题库数据和解题规则，使用 Android 原生触屏 UI 重做。

推荐技术方向：

- Kotlin + Jetpack Compose：适合快速调整屏幕布局和状态界面；
- Room 或 DataStore：保存进度、标记和成就；
- `assets/puzzles/*.json`：内置精选题库；
- 独立的 `TsumeCore`：处理棋盘、持駒、移动、升变和解答匹配；
- 以后如果桌面和 Android 需要完全共用规则核心，可以考虑 Kotlin Multiplatform 或 Rust 核心库。

第一阶段不建议用 WebView 直接套桌面页面。虽然可以复用 HTML，但触屏反馈、返回键、横竖屏和系统分享体验会比较差；而且用户已经明确 Android UI 要大改。

### Android UI 需要重做的部分

桌面版可以把题库、棋盘和统计同时放在屏幕上；手机屏幕更适合分层：

1. 首页：今日任务、连续天数、总完成数和开始按钮；
2. 题库页：5/7/9 手大按钮、进度环和标记题入口；
3. 解题页：棋盘占主要区域，持駒放在棋盘上下，操作按钮固定在底部；
4. 提示/答案：使用底部抽屉或弹窗，不挤压棋盘；
5. 统计页：成就卡片、分手数进度、错题回收；
6. 设置页：棋盘大小、音效、振动、深色模式和记录备份。

必须注意：

- 棋盘格触控区域不能太小；
- 不能依赖鼠标悬停提示；
- 选择棋子、选择目标、等待玉方应手要有明显状态；
- 横屏可作为可选模式，竖屏是默认模式；
- 适配刘海、状态栏和底部手势区域；
- 升变选择要在拇指容易触达的位置出现；
- 错误时用颜色、轻振动和文字同时反馈，但要提供关闭振动的选项；
- 不要把“完成题数”只放在统计深层页面，首页要能看到训练动力。

### Android 数据模型建议

题目数据建议统一成类似结构：

```text
Puzzle
  id
  mateLength
  initialPosition
  solutionTree
  quality
  source
  collection
  enginePolicy

Progress
  puzzleId
  attempts
  wrongAttempts
  solved
  marked
  bestSeconds
  lastPlayedAt
  solvedAt
  failedCount
  hintCount
  answerShown

TrainingSummary
  solvedCount
  attemptCount
  markedCount
  markedSolvedCount
  currentStreak
  achievements
```

桌面版当前线性 `solution` 数组先作为题目手数、参考手顺和无引擎时的回退数据；Android 以后可以把它转换成 `solutionTree`，再支持多个玉方应手分支和解答说明，但不把它当作唯一的用户着法判定器。
桌面版引擎桥接不建议原样搬到 Android：Android 版应把快速玉方应手作为可选的本地 worker，优先尝试稳定的 USI 长驻进程；训练规则只依赖合法王手和题目手数，应手引擎异常时再使用题库回退。

### Android 后续开发顺序

1. 把题库 JSON 格式固定并加版本号；
2. 把移动/吃子/打入/升变逻辑抽成无 UI 的核心模块；
3. 用单元测试覆盖 5/7/9 手题目；
4. 用 Compose 做竖屏解题页；
5. 加 Room/DataStore 记录和成就；
6. 加题库更新和记录备份；
7. 最后再做动画、主题、音效和成就视觉包装。
8. 接入可选的快速玉方应手引擎和严格手数设置，做低性能设备回退测试；不把引擎首着或“证明为诘”作为基础训练门槛。

## 八、最近一轮视觉与统计更新

本轮把页面从偏蓝灰的通用卡片风格统一为暖木色和风棋盘：

### GitHub 发布准备

当前便携包可以直接运行，但 outputs 目录还不是 Git 仓库。建议 GitHub 仓库保留源码、题库、说明文档和打包脚本；大型可执行文件和最终压缩包可以作为 Release 附件，避免每次代码提交都携带约 90 MB 的发行包。真正推送前需要确定仓库地址和登录账号，再设置远程仓库、首次提交和 Release 流程。
